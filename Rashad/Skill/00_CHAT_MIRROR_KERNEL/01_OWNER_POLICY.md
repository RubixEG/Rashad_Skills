# Owner Policy — Always-On Behavioral Defaults

STATUS: ACTIVE
SCOPE: behavioral defaults only. Current explicit user instructions always override these defaults.

## Product behavior
- `RFP Summary` means Rashad's defined `INTERNAL_PURSUIT_BRIEF` product by default, not a generic text summary.
- Default delivery is an artifact when the runtime can execute the defined production contract.
- `content only`, `analysis only`, or an equivalent explicit request is the exception.
- Never ask the owner to choose text vs artifact for a normal `RFP Summary` request.

## Language
- Follow the engagement/RFP language unless the user explicitly overrides it.
- Arabic RFP/client-facing output uses Arabic visible headings, labels and structural language.
- Internal English IDs may exist but must not leak into Arabic visible output.
- Arabic client-facing natural-language numerals use Arabic-Indic digits under the current v2.5 policy; exact machine/technical identifiers are preserved when conversion would corrupt them.

## Cover and imagery
- RFP Summary cover uses an engagement-specific hero unless explicitly waived.
- Arabic cover: hero-image zone left; native identity/text zone right under the current cover authority.
- Cover/Golden Visual Master imagery may include relevant contextual people, Saudi flags, devices, screens, dashboard-like cues, architecture and environmental detail. These are visual context, not authoritative page copy or brand evidence.
- Image generation may produce the complete **Golden Visual Master visual composition** for one page. Exact production text/numbers and exact Rubix/client logos remain native governed overlays.
- A generated hero alone can never complete the RFP Summary product.

## Brand
- Use only current verified Rubix assets.
- Never generate/recreate/approximate the Rubix logo.
- Historical logos, fonts, colors and exact layouts are never current production authority.
- No black or near-black client-facing slide backgrounds.

## Artifact behavior
- Meaning precedes layout.
- Required sequence: evaluator/management question → thesis → evidence → Artifact Intent → simplest-fit Communication Strategy → information structure / semantic relationship model → page-specific Visual Concept → Art Direction → internal concept search as needed → `PRODUCTION_PAGE_RENDER` → actual-pixel QA → repair → exact-file Delivery Gate. Archetype/topology/geometry is downstream only when the chosen strategy genuinely needs relational structure.
- Do not start from cards, section names, old slides, templates or decorative shapes.
- Generic equal-card grids are not a universal fallback.
- Artifact Council precedes layout/safety repair. Safety may repair geometry but may not destroy analytical meaning.

## Risks
- Risks must address proposal, technical, financial/pricing, estimation, staffing/mobilization, dependencies, delivery, acceptance, launch/cutover, hypercare, operations/support, handover/BAU or material contractual exposure.
- Do not publish generic tender-booklet observations as risks.

## Clarifications
- Clarifications must sound like questions from a senior team that understands the scope.
- A question survives only if answer A vs B materially changes scope, solution, effort, price, team, schedule, acceptance, launch, operations, responsibility split, assumption or qualification.
- Do not ask platform-obvious/Etimad-obvious questions unless the specific competition creates an exception or conflict.

## Owner-interaction default
Do not ask the owner for information that can be obtained from:
1. current explicit instructions;
2. this Owner Policy;
3. current RFP/evidence;
4. current Engagement State if provided;
5. an active v2.5 authority/default;
6. a safe, labeled, non-blocking assumption or information-gap record.

Ask only when the missing fact is truly blocking, cannot be derived, and cannot safely remain an assumption/gap.

## Cover quality lock
- Every normal RFP Summary cover must use a newly generated, engagement-specific premium hero image; abstract placeholder vectors/diagrams do not satisfy this requirement.
- Arabic cover visual grammar is hero-left / native identity-right by default.
- Relationship-heavy analytical pages must prove Artifact Engine execution and may not downgrade to generic cards/tables merely for rendering convenience.

## Co-brand signature lock
- Every branded client-facing page uses the physical left-side signature `Rubix | Client` unless the owner explicitly overrides it for the current engagement.
- Rubix is always the far-left mark; RTL never reverses this order.
- Both marks must be verified transparent-background PNG production assets.
- Match visible/optical height, preserve aspect ratio, and never crop, stretch, mirror, recolor or generate either logo.
- Missing/unverifiable client logo may block final branded release but must never be approximated.

## Section visual-coherence and depth lock — v2.6.4
- Preserve the canonical 24 RFP Summary logical roles; do not add/remove roles merely to fix depth.
- A role expands to multiple pages whenever one page cannot satisfy its Understanding Depth Contract without compression.
- For multi-page analytical sections, run the Section Visual Board Director and create one Golden Section Board/Section Anchor before page-master generation.
- The Golden Section Board is reference-only and contains no production text, logos, numbers, dates, or client facts.
- Page-by-page Golden Visual Masters are the preferred high-fidelity execution path when the native composer would materially weaken the approved artifact.
- HTML/PDF/PPTX must preserve the approved master/board topology, focal hierarchy, whitespace strategy, section rhythm and master underlay; mapping is not a redesign opportunity.
## Consulting-grade visual quality default
- Client-facing analytical pages must target top-tier consulting quality suitable for Saudi ministries, authorities, public funds and government entities; attractive decoration alone is insufficient.
- Use the audited historical proposal corpus only as an abstract quality benchmark; never copy legacy branding, exact layouts, client facts or assets.
- A relationship-heavy artifact may not be downgraded to generic cards for rendering convenience.
- A source visual is not approved until final rendered outputs preserve its topology, hierarchy, RTL, brand and readability.
## v2.6.4.4 Golden Visual Master default
- Plan the full deck visual system before generating page images.
- Generate one Golden Visual Master per physical page, normally in 4–6 page batches.
- Every page generation reuses the frozen Style Anchor Set + Section Anchor + adjacent-page continuity reference; never rely on chat memory alone.
- Equal-card grids are a justified artifact family only, never the default renderer fallback.
- Final production overlays exact text/numbers/logos on the frozen master; do not rebuild the visual artifact with weaker HTML/PPTX primitives.
