# Historical Proposal Corpus — Visual & Storytelling Council Audit

**Classification:** REFERENCE ONLY
**Corpus reviewed:** historical Rubix proposal archive containing 34 proposal deliverables (31 PDF + 3 PPTX in the audited archive). No source proposal binary is embedded in the final skill.

## Representative engagements reviewed
The audit sampled long/short and Arabic/English materials across technical proposals, strategy, market research, events, quality/transformation and other consulting scopes, including representative MEWA, MWAN, KAU, NCPD, SDB, SSP and VAC-style proposal material.

## What the Artifact Engine may learn

### 1. Evaluator navigation
Strong proposals help the evaluator understand where criteria, solution logic and evidence are addressed. The principle is reusable; old navigation graphics are not.

### 2. Methodology as a narrative, not a single page
The stronger historical work builds methodology over several pages:
`concept → framework → application → outputs → governance/measurement`.
Rashad should preserve this narrative depth when the information warrants it.

### 3. Relationship-first visualizations
Useful historical relationships include:
- ecosystem/value-chain maps;
- current-state → future-state transitions;
- phase/track roadmaps;
- decision/governance layers;
- deliverable/evidence architecture;
- role-to-workstream/output maps;
- strategy-to-operating-model connections.

The current Artifact Engine must reconstruct these relationships in the current Rubix design language rather than copy coordinates.

### 4. Proof rhythm
Strong case-study/evidence sequences typically move:
`context → intervention → output → proof/impact`.
This is preferable to logo walls or unstructured credential dumps.

### 5. Page rhythm
Useful rhythm alternates:
`analytical density → synthesis/decision → evidence/proof`.
This prevents a long deck from becoming 50 identical card grids.

## Weaknesses / anti-patterns to prohibit
- dark magenta/black full-slide dependency;
- legacy logos and client identity;
- repeated 4/5-card grids regardless of information relationship;
- decorative hexagons/rings/shapes without analytical purpose;
- shrinking text to preserve a template;
- using tables for content that is fundamentally a system/dependency/sequence;
- screenshot/certificate walls;
- inconsistent near-magenta shades;
- duplicated narrative across sections;
- client-specific images/facts leaking into another engagement;
- weak physical RTL ordering;
- exact old layouts being promoted to “current” templates.

## Artifact Engine decision rule
Historical proposals answer:
**“What visual relationship or storytelling move worked here?”**

They do not answer:
**“Which old slide should we copy?”**

Required pipeline:
`Current evidence → evaluator/management question → thesis → information relationship → artifact family → original composition → current Rubix palette/logo → RTL/geometry → QA`.

## Release boundary
A historical pattern can be used only when:
- the current page has the same information relationship;
- the current evidence supports the semantic nodes;
- current brand/theme rules are applied from scratch;
- no old client/logo/text/coordinates are retained;
- the Theme & Color Governor and Artifact/Brand/RTL council pass it.
